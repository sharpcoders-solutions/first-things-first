# 🧠 C# Fundamentals: Anonymous Types and dynamic

⏱️ Reading time: 7 minutes  
✍️ Author: Vitor Santos + 🤖 Copilot

## 🚀 Introduction

So far, you've learned:

- Tuples and `ValueTuple` for grouping values without creating a formal type  
- When to prefer a tuple and when to prefer a `record`  

Tuples handle grouping two or three values well. But there's an even more informal feature — creating an object with named properties without declaring **any** type, not even a tuple. And on the opposite end, there's a way to fully abandon compile-time type checking. Let's look at both, and why one is useful while the other almost never is.

👉 **Let's get to know anonymous types and `dynamic`**

---

# 💡 Anonymous Types: an object without declaring a class

```csharp
var person = new { Name = "Vitor", Age = 30 };

Console.WriteLine(person.Name); // Vitor
Console.WriteLine(person.Age);  // 30
```

👉 **Anonymous type = a class generated by the compiler at compile time, with no visible name in your code**

Behind the scenes, the compiler creates a real class (something like `<>f__AnonymousType0`), with `get`-only properties, `Equals`, `GetHashCode`, and `ToString` implemented automatically — you just never see its name

---

# 🎯 Where anonymous types shine: LINQ projections

```csharp
var orderSummary = orders
    .Where(o => o.Status == OrderStatus.Delivered)
    .Select(o => new { o.Id, o.Customer, Total = o.Items.Sum(i => i.Subtotal) });

foreach (var summary in orderSummary)
{
    Console.WriteLine($"{summary.Id} - {summary.Customer}: {summary.Total:C}");
}
```

👉 Remember the extension methods and LINQ post? `Select` is the classic spot where anonymous types show up — you project just the fields you care about, without needing to declare a DTO for a result used a single time, inside a single method

---

# ⚖️ Equality on anonymous types: by value

```csharp
var p1 = new { Name = "Vitor", Age = 30 };
var p2 = new { Name = "Vitor", Age = 30 };

Console.WriteLine(p1 == p2);      // false — doesn't overload the == operator
Console.WriteLine(p1.Equals(p2)); // true — generated Equals compares by value
```

👉 Anonymous types compare by value via `Equals` — the same behavior as a `record` (remember?) — but only if the properties have the same names, in the same order, with the same types. That happens because the compiler reuses the **same generated class** for two anonymous types with that identical signature

---

# 🚧 The limitations: why not use anonymous types everywhere

```csharp
public object CreatePerson() // ❌ can't declare the return type
{
    return new { Name = "Vitor", Age = 30 };
}
```

👉 **An anonymous type can never be a method's declared return type, nor a parameter** — because it has no name to write in the signature. This limits its use to local scopes: variables, LINQ projections, and code that never leaves the method where it was created. For anything crossing a method boundary, a `record` is the right tool

---

# 🎭 `dynamic`: abandoning compile-time type checking

```csharp
dynamic value = 10;
value = "now I'm a string";
value = new { Name = "Vitor" };

Console.WriteLine(value.PropertyThatDoesNotExist); // compiles! But blows up at runtime
```

👉 **`dynamic` = a type that turns off compiler checking; errors that would normally show up at compile time only show up at runtime**

Unlike `object`, which requires an explicit cast to access members, `dynamic` lets you call any method or property — and the compiler simply accepts it, trusting it'll exist when the code actually runs

---

# 🕵️ When `dynamic` is actually justified

```csharp
// COM interoperability (Excel, Word) — the classic scenario
dynamic excel = Activator.CreateInstance(Type.GetTypeFromProgID("Excel.Application"));
excel.Visible = true;

// Working with JSON of a truly unpredictable structure
dynamic json = JsonConvert.DeserializeObject("{\"field\": \"value\"}");
Console.WriteLine(json.field);
```

👉 The legitimate cases are rare: interoperability with old COM libraries, or parsing JSON with a structure unknown at compile time. Outside of that, `dynamic` is usually a sign that a better design (interfaces, generics, or even `object` with pattern matching) would solve the same problem with type safety

---

# ⚠️ Common Mistakes

- Using `dynamic` to "save time" by avoiding defining a type, losing all compiler help and IntelliSense  
- Returning `dynamic` from a public API method, making the contract completely opaque to consumers  
- Trying to use an anonymous type as a method's return type, running into the local-scope limitation  
- Confusing `dynamic`'s performance with static types — calls through `dynamic` go through runtime resolution, slower than regular calls  

---

# 📌 Conclusion

- Anonymous types create objects without declaring a class, ideal for local LINQ projections  
- Anonymous types compare by value, but can never leave the scope of the method where they were created  
- `dynamic` turns off compile-time type checking, pushing errors to runtime  
- `dynamic` is only justified in rare scenarios: COM interoperability, or JSON with a truly unpredictable structure  

👉 Between tuples, anonymous types, and `dynamic`, you now have the full picture of how C# handles data that doesn't deserve (or can't have) a formal named type
